# Scheduled Tweet Ideas  

## Editable Settings  

- Generate 3 tweet ideas per run. Never append more than 3.  
- Work in `/home/pimania/notes`.  
- Append to `inbox-index.md`.  
- Use `tweet-ideas-accepted.md` and `tweet-ideas-rejected.md` as feedback files.  
- Prefer blog-post notes, but do not exclude other strong source notes.  

## Task  

- Read `writing-ideas-index.md`, `twitter-index.md`, `inbox-index.md`, `tweet-ideas-accepted.md`, and `tweet-ideas-rejected.md`.  
- If either feedback file is missing, create it with a single `# tweet ideas accepted` or `# tweet ideas rejected` heading before generating ideas.  
- Use `writing-ideas-index.md`, `twitter-index.md`, and recent/relevant notes to locate source material.  
- Also treat notes containing `` as blog-post notes.  
- Generate exactly 3 fresh tweet ideas when enough usable source material exists. If fewer than 3 usable ideas exist, append only the usable ideas and mention the shortfall in the final response.  
- Append them under `## Active inbox` in `inbox-index.md`.  
- After appending, run `/home/pimania/notes/.agents/skills/scheduled-tweet-ideas/scripts/open_feedback_tabs.sh` to open the feedback notes in VS Code and focus `inbox-index.md` last.  

## Source Selection  

- Emphasize blog-post notes: Markdown files with blog frontmatter such as `articleUrl:`, `category: blog`, or `layout: post`.  
- Aim for blog-post notes to supply most ideas when they contain usable material.  
- Also use non-blog notes when they contain concrete, publishable material related to writing or Twitter ideas.  
- Do not invent claims, examples, data, or mechanisms not supported by the source material.  
- If no usable source material is available, do not append empty or invented items. Report that no tweet ideas were added.  

## Feedback And Reuse  

- Treat accepted ideas as positive examples of style, clarity, specificity, density, and structure.  
- Treat rejected ideas as feedback about what failed. Reuse a rejected underlying idea only when the new version addresses the rejection reason, such as making a vague idea concrete, clarifying an unclear point, shortening an overlong draft, or adding missing specificity.  
- If a rejected idea has no explicit rejection reason, treat it as weak negative evidence: do not reuse the same framing, and only revisit the underlying idea when the new version is materially clearer and more specific.  
- If the rejection reason rejects the premise, content, or claim itself, do not reuse that idea.  
- Do not repeat accepted ideas or prior generated ideas from `inbox-index.md`.  
- Do not repeat any previous idea with only cosmetic wording changes.  
- Prefer concrete, high-signal ideas grounded in the source over generic social-media prompts.  
- Each idea should work as a standalone tweet for readers who have not read the notes or blog post.  

## Output Format  

Append only this block under `## Active inbox` in `inbox-index.md`:  

```markdown  
# tweet ideas YYYY-MM-DD  

first sentence of first tweet idea  
second sentence of first tweet idea  

---  

first sentence of second tweet idea  
second sentence of second tweet idea  

---  

first sentence of third tweet idea  
second sentence of third tweet idea  
```  

Use `---` on its own line between tweet ideas. Do not use checklist bullets. Put each sentence on its own line. Write generated tweet text in lowercase, even where casing is really actually necessary for urls, quoted names, code, or units.  

## Quality Gate  

- Make each idea info-dense, succinct, and clear for someone who has not read the source note.  
- Prefer multiple short or medium sentences over very long sentences that strain attention.  
- Make the tweet concrete enough that it names the relevant mechanism, example, constraint, tradeoff, or question where that improves clarity.  
- Do not force every tweet into a fixed template; use the concrete detail that best fits the source.  
- Avoid vague claims such as "this matters", "the key issue", or "the real problem" unless the sentence names what makes it matter.  
- Avoid filler wording, hand-wavy abstractions, AI-ish phrasing, generic engagement bait, and unsupported implications.  
- Avoid novel terms and unexplained acronyms unless the tweet defines them in plain language.  
- It is ok if an idea is more than 280 characters or could become a thread.  

## Rules  

- Do not ask follow-up questions.  
- Do not modify source notes other than `inbox-index.md` and the two feedback files.  
- Fail clearly if required files cannot be read or `inbox-index.md` cannot be written.  
- If `open_feedback_tabs.sh` fails, report the failure clearly instead of silently using another editor or command sequence.
